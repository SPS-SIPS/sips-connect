# Domestic outgoing payment localId idempotency

Revised 10 November 2026. Domestic requests use the bank's existing `localId`, mapped to `EndToEndId`, as the idempotency key. `txId` remains optional and is generated by SPS Connect when omitted. PAPSS keeps its existing `txId` contract.

## Contract tests

`Packages/SIPS.Core.Tests/Tests/OutgoingTransactionIdempotencyTests.cs` runs the production domestic outgoing handler with controlled persistence/network doubles.

| Cases | Expected behavior |
|---|---|
| 3: null, empty or whitespace localId | Bad request without signing, storage or network effects |
| 4: original successful, rejected, pending or uncertain payment | Original status and original txId/EndToEndId; no new signing or submission |
| 3: same localId with changed amount, beneficiary or optional txId | Original payment returned with explicit replay notice; original data untouched |
| 1: lost response and retry through a fresh handler | Same generated transaction ID returned; only one submission |
| 1: retry while original network request is in progress | Pending replay; only the original is submitted |
| 1: simultaneous first inserts | Database winner submits; loser replays pending original |
| 1: different localIds with identical payment details | Distinct instructions; neither requires a bank-supplied txId |
| 1: database unavailable | No network submission |

Run:

```bash
dotnet test Packages/SIPS.Core.Tests/SIPS.Core.Tests.csproj -m:1 \
  --filter FullyQualifiedName~OutgoingTransactionIdempotencyTests
```

The previous test-first baseline targeted a mandatory txId and had 13 failures out of 15. That design was superseded locally before publication because it would break banks that omit txId. These revised tests deliberately submit payments without txId. Existing timeout/token fixtures also continue to omit txId.

## Real PostgreSQL coverage

`SIPS.Connect.PostgresTests/OutgoingPaymentIdempotencyTests.cs` uses PostgreSQL migrations and independent DbContexts. Only network/signing boundaries and a deterministic insertion barrier are mocked.

- Simultaneous first submissions with the same localId generate separate candidate txIds, but the dedicated domestic index admits only one. Both callers receive pending; one network submission and one payment transaction exist. Both contexts remain usable after the conflict.
- A fresh service/container replays an uncertain original and its later reconciled final state without another network submission or changing the original amount/beneficiary.
- An inbound message with the same EndToEndId does not claim a domestic outgoing idempotency key.
- A PAPSS-profile message with the same EndToEndId does not claim a domestic outgoing key.
- An unambiguous historical domestic row without the new key is replayed using its stored txId.
- Multiple historical domestic rows sharing localId return a reconciliation conflict instead of selecting an arbitrary payment.

Supply an isolated database connection through `SIPS_TEST_POSTGRES_CONNECTION` and run:

```bash
dotnet test SIPS.Connect.PostgresTests/SIPS.Connect.PostgresTests.csproj -m:1 \
  --filter FullyQualifiedName~OutgoingPaymentIdempotencyTests
```

## Database and deployment requirements

Apply `AddDomesticOutgoingLocalId` before deploying. It adds nullable `DomesticRequestId` to ISO messages, a unique `(FromBIC, DomesticRequestId)` index, and a non-unique domestic EndToEndId lookup index. Only new domestic outgoing initiations populate the new key. Historical rows, incoming traffic and PAPSS traffic are not backfilled or subjected to new global EndToEndId uniqueness.

A bank must provide a unique, non-empty localId per payment instruction and preserve it across retries. Reusing localId for a genuinely new payment returns the original payment, even if amount or beneficiary differs. Upgrade all domestic initiators together: older binaries do not populate the new key and must not remain mixed writers during activation. Inventory and reconcile historical duplicate IDs before rollout.

The existing network txId remains necessary for status and return correlation. This change preserves that value and does not replace network references with localId.

## Limits

Tests simulate network timeouts and service-context recreation; they do not contact the payment network or kill live processes mid-commit. Existing timeout/status recovery workers remain responsible for unresolved durable payments. Bank-side ledger posting still requires its own idempotency. This work does not claim exactly-once financial posting.

The API suite has a known captured-recall certificate validity/trust test failure reproduced on unchanged main. That issue is separate from domestic payment retry handling.

## Verified revised results

The revised localId implementation passed 207 core tests (7 existing skips) and 7 PostgreSQL cases, including races with omitted and supplied txId, historical records, and network/profile isolation. API regression remains 250 passed and the same 1 pre-existing certificate-fixture failure. These results were obtained locally; no numbered image release was published for this change.
